## Задача одной строкой

Открытие трейса читает индекс **каждого** сегмента целиком (38 % байтов `.trc`), потому что
у trace id нет временных границ, а внутрисегментный индекс — несортированный линейный список.
Замерено: 168 сегментов → 9 МБ с диска и 12 МБ распаковки, чтобы вернуть 5 спанов.

## Инвариант, который нельзя нарушать

**Отрицательный ответ индекса имеет силу только внутри `Covered`.** Сегмент пропускается,
только если он покрыт индексом И индекс его не назвал. Всё остальное читается как сегодня.
Из этого следует всё остальное: частичное включение, фоновый backfill, откат в один шаг,
и невозможность получить неправильный ответ из-за индекса — только медленный.

  - `TraceIndexRun` (level, path, minKey/maxKey, entryCount, **`CoversSegment`**);

- **`tests/Ameto.Storage.Tests/TraceManifestTests.cs`** — 20 тестов, зелёные.

### Найдено по дороге (и исправлено)

`TraceIndexRun` изначально сопоставлялся сегменту **по пути файла**, а путь у прогона — это
его собственный `.tix`, никогда не `.trc`. Ничего не совпадало, и прогоны переживали свои
сегменты. Отсюда появилось поле `CoversSegment`, и вместе с ним — явная разница между двумя
видами прогона:

- **по-сегментный** (`CoversSegment != null`) умирает вместе с сегментом;
- **слитый** (`CoversSegment == null`) переживает: в нём живые записи других сегментов,
  а записи ушедшего становятся мусором, который фильтруется на чтении по «есть ли ещё такой
  segId в каталоге» и физически исчезает при следующей компакции индекса.

Это и есть причина, по которой **надгробия (tombstones) не нужны**. Тест:
`A_merged_run_outlives_the_segments_it_covers`.

- **Каталог вшит в жизненный цикл сегмента** (`TraceStorageEngine`):
  - `SpanSegmentInfo.SegmentId` + `WithSegmentId`; **0 = «вне каталога»**, читается как сегодня;
  - конструктор грузит манифест первым делом;
  - `CompleteFlush` — id выделяется **после** rename `.trc` и **до** подмены `_coldSegments`;
  - `CompactOnePass` — `ReplaceSegments` до подмены снапшота, id исходников уходят навсегда;
  - `PruneAsync` — `RemoveSegments` перед удалением файлов;
  - `ReconcileCatalog` в `LoadColdSegments` — **диск авторитетнее каталога**: файл без записи
    усыновляется, запись без файла удаляется (по `File.Exists`, а не по «нет в этом скане» —
    скан пропускает публикуемый сегмент, и он не «пропал»);
  - каждая точка обёрнута в try/catch: сбой каталога стоит имени, а не флаша.
- **`tests/Ameto.Storage.Tests/TraceCatalogLifecycleTests.cs`** — 7 тестов: имя переживает
  рестарт, старые сегменты усыновляются, мёртвая запись выпадает, компакция не переиспользует id,
  retention чистит каталог, убитый манифест стоит только имён.

481 storage + 277 integration зелёные.

### Найдено по дороге (и исправлено)

Дельта-кодирование смещений не умеет шаг назад, а писатель для убывающего шага писал
**абсолютное** значение — читатель же всегда складывает. `[200000, 199999]` возвращалось как
`[200000, 399999]`: молча, и это указатель на спаны, которые трейсу не принадлежат.
Инвариант теперь устанавливается на входе (`Add` сортирует, не трогая массив вызывающего),
а не «чинится» в кодировщике. Тест: `Offsets_round_trip_including_large_and_non_contiguous_ones`.

### Сделано — запись и чтение

- **`SpanWriter.Write`** получил `onTraceIndex`: отдаёт ту карту trace→offsets, которую и так
  строит. Не перечитываем готовый файл — индекс из второго независимого прохода может
  разойтись с сегментом, который описывает.
- **`TraceIndexStore`** — открытые прогоны: bloom + разрежённый индекс в RAM.
  Намеренно **не решает**, можно ли пропустить сегмент: у него только половина факта.
- **`SpanReader.ReadTraceAtAsync`** — тот же обход, но по готовым смещениям, без
  `ReadTraceOffsets`. Полный id всё равно сверяется, поэтому коллизия усечённого ключа даёт
  пустой результат, а не чужие спаны.
- **`TraceStorageEngine`**: `.tix` пишется во flush и в компакции; прогоны закрываются перед
  удалением файлов; `.tix` добавлен в `DeleteSegmentFiles`; `Dispose` освобождает нативную
  память bloom'ов.
- **Правило чтения** (`GetTraceAsync`): сегмент пропускается, **только если**
  `SegmentId != 0` И `IsCovered(SegmentId)` И ни один прогон не назвал в нём этот трейс.
- **`WithdrawCoverage`** — прогон не открылся, значит покрытие снимается сразу.
- **Счётчики** `SegmentsOpenedByLastTraceLookup` / `Skipped` — чтобы тест доказывал экономию
  работы, а не только правильность ответа.

**Замерено (`TraceIndexLookupTests`):** 12 сегментов, трейс в одном →
**открыт 1, пропущено 11**. Несуществующий трейс → **открыто 0 из 10**.

### Найдено по дороге (и исправлено)

Поиск блока предполагал уникальные ключи. `UpperBound` возвращал **последний** блок с таким
первым ключом, а когда одним ключом занято несколько блоков подряд (ключ — первые 8 байт
id; продюсер, меняющий только младшую половину, или обычная коллизия), находился хвост
серии, а начало терялось. Поймал `TraceFlushVisibilityTests`, где все 300 трейсов имеют
одинаковую старшую половину: ожидалось 2 спана, возвращалось **0**, молча.
Теперь `FirstBlockThatCouldHold` отступает назад по блокам с тем же первым ключом, а обход
идёт вперёд **до первого строго большего ключа**, а не «пока блок кончился на ключе».
Тест: `One_key_spanning_many_whole_blocks_is_found_from_its_first_entry`.

### Сделано — миграция старых сегментов

- **`SpanReader.ReadTraceIndex`** — весь индекс трейсов сегмента разом. Это ровно то дорогое
  чтение, которое индекс убирает с пути запроса; здесь оно платится **один раз на сегмент**,
  в фоне, и покупает все последующие обращения.
- **`TraceStorageEngine.BackfillNextSegment`** — ровно один непокрытый сегмент за вызов.
  Темп задаёт вызывающий. Порядок: собрать прогон → fsync → rename → **только потом**
  `MarkCovered`. Сегмент, который не удалось проиндексировать, попадает в `_backfillFailed`
  и больше не берётся (иначе воркер вечно крутится на нём).
- **`TraceIndexBackfillMode`** (`Off` / `Idle` / `Eager`) + `TraceIndexBackfillWorker`.
  По умолчанию `Idle`: один сегмент, пауза 5 с; когда работы нет — тишина на 5 минут.
- **Конфиг** `Ameto:Traces:IndexBackfill` (строка, чтобы опечатка не роняла старт) →
  `AddAmetoTracing(dataDir, mode)`; описано в `config.yml`.
- **`DisableTraceIndexForTest`** — откат: снять покрытие и закрыть прогоны.

**Замерено (`TraceIndexBackfillTests`):** легаси-инсталл из 6 сегментов, `0/6` → открыто 6;
после бэкфила `6/6` → **открыт 1, пропущено 5**, ответ побайтово тот же. На середине
миграции (`4/8`) все трейсы возвращаются целиком, а отсутствующий стоит 4 открытия из 8.

## Стадия 1 — что уже решено, чтобы не передумывать

- Ключ — **первые 8 байт** trace id. Коллизия ≈ 2·10⁻⁷ при 2,8 млн трейсов и это
  ложноположительный ответ (откроем лишний сегмент, сверим полный id), а не неверный.
- Значение — `segmentId | offsetCount uvarint | offsets uvarint delta`.
- Формат `.tix`: header 28 B → LZ4-блоки записей → разрежённый индекс (16 B на блок) →
  bloom (`Ameto.Indexing.SegmentBloomFilter`, переиспользуется как есть) → footer 20 B.
- **Миграция старых сегментов — опциональна и фоновая** (см. ниже).

## Миграция старых трейсов (требование заказчика)

Старые сегменты, записанные до появления индекса, должны попадать в индекс — **как опция**.

- Конфиг: `Ameto:Traces:IndexBackfill` со значениями `off` / `idle` / `eager`.
  Значение по умолчанию — обсуждается; склоняюсь к `idle`.
- Механика: фоновая задача берёт **один** сегмент за раз, читает его внутрисегментный индекс
  трейсов (ту самую дорогую операцию, которую мы убираем — но однократно на сегмент),
  пишет `.tix`, fsync, rename, затем `MarkCovered`. Порядок именно такой: покрытие
  объявляется последним, поэтому падение в любой момент стоит пересборки одного прогона.
- Пауза при давлении: не работать, пока `RamPressureService` жалуется, и держать паузу
  между сегментами, чтобы не конкурировать с ингестом на 512 МБ.
- Прогресс наблюдаем: `covered / segments` — то, что нужно в диагностическом эндпоинте.
- Откат: `ClearCoverage()` + удалить `.tix`. Данные не трогаются вообще.

## Стадия 2 — компакция прогонов в уровни

### Сделано

- **`TraceIndexRun.CoversSegment` → `CoveredSegments` (массив).** Это не косметика: покрытие —
  это право **пропустить** сегмент, и его нужно уметь отозвать в тот момент, когда прогон не
  открылся. С одним id это работает; у слитого прогона движок знал бы, что заявка провалилась,
  и не знал бы — чья. Заявка, которую некому отозвать, это ровно тот молчаливый недоотчёт,
  ради запрета которого всё и строится.
- **Правило удаления прогона: `KeepRuns`** — прогон уходит, только когда ушли **все** покрытые
  им сегменты. По-сегментный (один id) умирает вместе со своим; слитый переживает потерю
  одного, потому что держит живые записи остальных.
- **`TraceIndexCompactor`** — `SelectMergeBatch` (низший переполненный уровень, мелкие первыми,
  до 32 за раз) + `Merge` (потоково, по блоку на вход).
- **`TraceIndexReader.EnumerateEntries`** / **`TraceIndexWriter.AddRaw`** — перенос записей
  между файлами без повторного вывода ключа.
- **`TraceStorageEngine.CompactIndexOnce`** — одно слияние за вызов; воркер зовёт его
  **после** бэкфила (сначала покрытие, потом консолидация).

### Два свойства, на которых держится безопасность

1. **Покрытие не меняется слиянием.** Слитый прогон несёт объединение покрытий входов, манифест
   трогается один раз — после rename. Нет момента, когда сегмент покрыт файлом, которого нет.
2. **Один нечитаемый вход отменяет всё слияние.** Продолжить — значит выпустить прогон, который
   заявляет покрытие входов и не содержит их записей: покрытый сегмент, чьи трейсы индекс не
   находит. Тест: `A_merge_whose_input_will_not_open_is_abandoned_rather_than_half_done`.

Мёртвые записи (сегмент ушёл) физически исчезают **только здесь** — это и есть то, чем в обычном
LSM были бы надгробия, и здесь оно бесплатно, потому что каталог уже знает, кто жив.

**Замерено:** 12 прогонов → 1, RAM 960 → 352 Б, все трейсы резолвятся, поиск по-прежнему
открывает 1 сегмент. 518 storage + 279 integration зелёные.

## Стадия 3 — формат v4

### Сделано

- **`SpanWriter.Version = 4`**: блок индекса трейсов пишется **пустым** (`traceCount = 0`).
  Смещение `traceIdxOffset` остаётся — три обхода блоков используют его как границу конца
  спан-блоков; уходит только payload.
- **`SpanReader`**: v4 принимается; `ReadTraceOffsets` для v4 падает на **скан спанов**,
  `ReadTraceIndex` для v4 строит карту тем же сканом (это и есть путь бэкфила).
- **`ReadTraceIdAndSkipV3`** — из спана читается **только** trace id, остальное пропускается,
  цепочка Δts прокручивается.
- **v3 не переписывается** ради этой правки: старые файлы держат свой индекс и читаются как
  раньше. v4 получают только новые сегменты (и всё, что перепишет компакция).

**Замерено:** 6000 спанов / 2000 трейсов → v3 142 786 Б, v4 84 578 Б, **на 40,8 % меньше**.

### Два бага, пойманных тестами (оба — реальные)

1. **Скан материализовал сегмент.** Первая версия `EnumerateTraceIdsInOrder` строила полный
   `SpanRecord` ради одного id. `SpanTraceReadBoundTests`: открытие трейса из **одного спана**
   выделяло **81,45 МБ** против 80,94 МБ чтения всего 50 000-спанового файла — то есть путь
   восстановления втихую вернул ту самую материализацию, которую убирал PR #63.
   После правки — **0,96 МБ**.
2. **Порванный `svcIdxOffset` стал тихим нулём.** Сдвиг разметки под v4 привёл к тому, что флип
   бита 32 попадает внутрь секции, разбирается как правдоподобный индекс, имя совпадает,
   `blkCnt = 0` → пустое множество блоков → фильтрованный поиск отдаёт 0 строк при 100
   у нефильтрованного. Закрыто двумя проверками: смещение обязано лежать между индексом трейсов
   и bloom-индексом, **и** разбор обязан закончиться ровно на `bloomIdxOffset`. Отвечаем `null`
   («не знаю»), а не исключением — потеря индекса стоит скорости, но не строк.

## Порог компакции — инверсия порогов

`HotFlushThreshold = 50_000`, а `CompactionThreshold` пускал в кандидаты только то, что
**меньше 10 000**. Сегмент, который пишет обычный сброс, не был кандидатом никогда: ни семенем,
ни в батче, ни слитым — до самого истечения TTL. Число сегментов росло с нагрузкой и не падало,
а поиск трейса опрашивает каждый холодный сегмент.

### Сделано

- **`CompactionThreshold` 10 000 → 60 000** (выше порога сброса).
- **Лимит памяти переехал в планировщик.** `MaxSpansPerPass` применялся **загрузчиком**, который
  останавливался, уже прочитав столько — то есть перебирал на размер последнего сегмента:
  ≤10 000 раньше, ≤50 000 теперь. `SelectCompactionBatch` теперь считает лимит при выборе, и
  батч из четырёх 50-тысячных держит ровно те же 200 000, что раньше держал батч из двадцати
  10-тысячных. **Замерено: batch of 4, 200 000 spans.**

### Потолок этой правки — честно

Дальше четырёхкратного сокращения N константа не даёт: результат слияния (~200 000 спанов) выше
порога и больше не сливается, а поднимать `MaxSpansPerPass` нельзя — `CompactOnePass`
материализует все спаны, и при измеренных 1 749 Б на спан это уже ~350 МБ на 512-МБ стенде.
Дальше нужен **потоковый merge** — отдельная работа по crash-critical пути.

Побочно: перезапись переводит существующие v3 в v4, то есть забирает те самые 40 % места.

### Ещё один баг, записанный как намерение

`SpanFormatV3Tests` содержал ассерцию `// Big v3 files are never candidates` — ровно этот дефект,
зафиксированный как ожидаемое поведение. Заменена на обратную, плюс новая: результат слияния
(200 000) кандидатом действительно не является.

## Ревью, раунд 1 — что изменилось после первого прохода ревьюера

Кратко, чтобы документ не расходился с кодом:

- **Порог компакции: `MaxSpansPerPass` понижен 200 000 → `2 × CompactionThreshold` (120 000).**
  Раздел выше утверждал, что поднятие порога «бесплатно», потому что пиковая память задаётся
  `MaxSpansPerPass`, а не порогом. Число действительно не изменилось — изменилась **частота**:
  при пороге 10 000 обычный 50-тысячный сброс не был кандидатом вообще, поэтому под нагрузкой
  компакция не запускалась и пик не достигался никогда. Починив это, мы сделали проход на ~350 МБ
  штатным на 512-МБ стенде. Теперь ~210 МБ, цена — сегменты сливаются по два, а не по четыре
  (двукратное сокращение N за проход вместо четырёхкратного). Равенство `2 ×` не круглое число:
  ниже него **верхний тир вообще не слился бы** — два сегмента по 59 999 спанов не помещаются.
  Счётчик спанов остаётся неверной единицей (те же 120 000 — это 24 МБ «голых» спанов или 210 МБ
  тяжёлых); правильный ответ — бюджет в байтах или потоковый merge, отдельной работой.

- **v4 пишется только по флагу `Ameto:Traces:SegmentFormatV4` (по умолчанию выключен).**
  Чтение v4 — безусловно. Причина: бинарь старее этого читает незнакомую версию как повреждение
  и **удаляет** сегмент с тремя сайдкарами. Откат через день после апгрейда стоил бы этого дня.
  Плюс этот билд больше не удаляет сегмент новее себя (`LooksLikeNewerFormat`), а помечает
  холодный тир неполным. 40,8 % забираются, когда флот целиком на этом билде — это дверь в одну
  сторону, и она подписана.

## Ревью, раунд 2

- **Трёхзначный `Lookup`.** `Found / NotPresent / Unreadable`: порванный блок, удалённый или
  занятый `.tix` и retired-ридер больше не выглядят как «трейса нет» — а именно этот ответ из
  **покрытого** рана разрешает пропустить сегмент. `TraceIndexStore` превращает `Unreadable` в
  множество id, которые **для этого запроса** считаются непокрытыми.
- **Ридеры считаются по ссылкам** (`TryAcquire` / `Release` / `Retire`): bloom лежит в
  `NativeMemory`, а store освобождал вытесненные ридеры сразу.
- **Покрытие снимается ДО lookup'а** одним снимком, а не спрашивается по сегменту после — иначе
  `MarkCovered` бэкфила успевает переключить сегмент в покрытые между двумя моментами.
- **Дублирующиеся смещения.** Компакция индекса намеренно держит слитый ран и его входы открытыми
  одновременно, поэтому один и тот же (сегмент, смещение) приходит дважды; обход стоял на месте и
  возвращал **префикс** трейса как целое. Дедуп после сортировки плюс курсор, переступающий копии.
- **Слияние индекса вообще не запускалось**: `backfill(ct) || merge(ct)` — короткое замыкание, а
  `BackfillNextSegment` возвращает `true` даже для сегмента, на котором **упал**. Пока оставался
  хоть один непокрытый сегмент, слияния не было — часами, на той установке, которой оно нужнее
  всего. И режим `Off` выходил из цикла целиком, хотя сбросы продолжали открывать ран на сегмент.
- **Батч слияния ограничен по записям** (`MaxEntriesPerMerge = 2 000 000`): merge держит все
  уцелевшие записи в одном writer'е, то есть пик — это **размер батча**, а не «по блоку на вход»,
  как утверждали два докстринга. Заодно исправлено заявление про «десятую часть памяти» — bloom
  масштабируется числом записей; выигрыш в **числе проб и открытых файлов**, а «960 → 352 Б» было
  артефактом крошечной фикстуры.
- **`ReadTraceIndex` возвращает `null`, когда не смог учесть все спаны.** Порванный
  `traceIdxOffset` может оказаться просто **меньше** истинного: он попадает внутрь файла, байт по
  нему разбирается, обход тихо кончается раньше. Сверяем число размещённых смещений с
  `spanCount` из заголовка (ровно одно смещение на спан). Проверка **не** в `ReadFooter`
  намеренно: бросок оттуда доходит до холодного скана, который читает бросающий футер как
  повреждение и **удаляет** сегмент. Честно про масштаб: сегодняшний fallback-скан упирается в ту
  же границу, поэтому ответ не меняется — закрывается **класс**, а не наблюдаемая потеря.
- **Ран, который больше никто не называет, закрывается и удаляется.** Живость считалась по
  **уходящей партии**, а не по выжившему каталогу, поэтому слитый ран держался памятью о
  сегментах, истёкших в прошлых поколениях, — и снять его было нечем: со второго старта его
  сегменты уже не покрыты, отзыв выходил сразу, файл переоткрывался и ругался при каждой загрузке
  вечно. Теперь живость — выживший каталог, отзыв — **по пути файла** (`DropRuns`), а покрытие
  пересекается с тем, что ещё обслуживается (только сужается).
- **Усыновление каталога — одно поколение.** Коммит переписывает и fsync'ает манифест целиком, а
  усыновление делало по два на сегмент: O(N²) байт и 2N сбросов на том самом старте, которому
  усыновлять больше всего. `AdoptSegments` — один коммит на любое N.
- **Откат доступен оператору:** `Ameto:Traces:IndexEnabled=false` + рестарт снимает все claim'ы и
  закрывает раны. Раньше это существовало только как тестовый шов.
- **Слитый ран не осиротеет при отказе записи манифеста:** `ReplaceRuns` обёрнут, ридер снимается
  и файл удаляется — иначе процесс держал bloom и хэндл до перезапуска, и каждое следующее
  слияние добавляло ещё один.
